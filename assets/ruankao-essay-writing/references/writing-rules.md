# 软考系分论文写作口径（2026-10 机考）

> 适用：系统分析师／系统架构设计师论文科目。本文件是插件内唯一的字数与结构真相源，`check-essay.ps1`、`make-essay-doc.ps1`、三个技能与 Web 面板都按本文件实现。
> 本文件只写公开的考试事实与自撰的写法说明，不摘录任何第三方付费资料的原文。

---

## 一、交付规格（硬约束）

机考论文分**摘要**与**正文**两个输入框，控件会实时计字符数：摘要框超过 300 字符无法继续输入，正文框超过 2500 字无法提交。因此按下面的双框口径写作与自检。

| 项目 | 要求 |
|---|---|
| 摘要 | **≤300 字（含标点）**，目标 280~300；独立成部分，但正文里不写「摘要」二字 |
| 正文 | **2000~2500 字（含标点）**，目标 2300~2500；2500 是机考硬上限 |
| 段落数 | 不锁死段数，按下面的部分配比自然成段；`check-essay.ps1` 只对摘要与正文总字数判硬项 |
| 标题 | 不写标题，也不写「摘要／背景／子题目」这些字眼 |
| 分点 | 不用「第一／第二」「首先／其次」「一是／二是」式列举，改用因果链叙事 |
| 人称 | 放开：可用「笔者／我们／我所在团队」；摘要里必须有身份交代（「本人」或「笔者」） |
| 引号 | 中文引号「“”」，正文不得出现直引号 |
| 时间 | 建设期（`YYYY年M月`）只写在摘要里，正文不重复 |
| 实例 | 每个论点至少一条项目内真实业务实例（业务场景＋数据量＋结果） |
| 收尾 | 写成效与对方法的理性认识，**不写**「不足之处／改进措施／下一步将」这套模板 |
| 分框分界 | 摘要段之后必须有**唯一一行**分界标记 `<!-- BODY -->`（也接受 `<!-- 正文开始 -->`）；它是 HTML 注释，门禁与生成脚本都会剥掉，不影响字数 |
| 交付形态 | `.md` 源稿 ＋ 两种 `.doc`：默认「分框标注版」（摘要框／正文框分栏＋各框字数），`-Plain` 出「无标注版」（考场粘贴用） |

## 二、部分与字数配比

| 部分 | 字数（含标点） | 内容要点 |
|---|---|---|
| 摘要 | ≤300 | 行业与业务痛点 → 我的角色与主要工作 → 本文的技术视角或创新点 |
| 项目背景 | 400~500 | 战略依据、投入资源、工期、独有业务模块；解释「为什么要做」 |
| 技术方法说明（回应子题目 2） | 400~500 | 题目列出的分类名称逐项写全、显性点题；说明各自在本项目中的落点 |
| 论点一（回应子题目 3） | 约 500 | 业务场景 → 关键决策 → 错误做法与后果 → 修正后的做法 → 结果 |
| 论点二（回应子题目 3） | 约 500 | 同上，换一个角度（另一类角色、另一类工件或另一类活动） |
| 结尾 | 300~450 | 成效（量化）＋对该方法的深入理解与边界认识 |

正文合计约 2000~2400，正好落在机考 2000~2500 区间内。

## 三、摘要怎么写

摘要不写「摘要」二字，直接起笔，三段意思串成一段：

1. **行业与业务背景**：本行业的业务特点与当下痛点，点明项目要解决什么，突出行业特色而不是通用套话。
2. **我的角色与任务**：用「本人」或「笔者」交代在项目中的岗位与具体职责，落到可验证的工作项。
3. **本文视角**：说明本文要论述的技术方法为什么适配这个业务，指出其中的关键判断或创新点。

摘要里必须出现项目名称、建设期与投资额（金额带「万」）、项目角色，这三项同时是门禁的检查项。

## 四、项目背景怎么写

这个部分考察站位，不是考技术清单。常见的低分写法是罗列六七个框架名（SpringBoot、Vue、Redis……）而对建设目的一字不提。

- 写清**战略依据**：业务侧的压力、合规要求、竞争或政策变化；
- 写清**投入资源**：投资规模、团队规模与构成、建设期；
- 写清**独有业务模块**：用本项目特有的业务场景（如信贷的「额度测算」「贷后预警」），避免「用户管理」「权限管理」这类通用模块；
- 用「概括＋理由」介绍技术栈：选它是因为什么业务特性，而不是把技术名堆成一句。

## 五、技术方法说明（回应子题目 2）怎么写

题目第 2 问通常是理论性的、概念性的：要你概述某个方法、模型或流程的分类。这部分是显性点题的得分区。

- 题目列出的分类名称**逐项写全**，用词与题目一致，一个不漏；
- 每个分类用一两句说清「是什么」，再补一句「在本项目中落点在哪」；
- 字数写到 400~500：漏写常见，但字数太少会让阅卷认定作答态度不足；
- 漏写不等于乱写：如果连题目在问什么都没把握，换题。

敏捷题（2023/05 系分试题三）需要写全的是：角色（产品负责人、Scrum Master、开发团队）、工件（产品待办列表、迭代待办列表、产品增量）、活动（迭代、迭代计划会议、每日站会、迭代评审会议、迭代回顾会议）。

## 六、论点展开（回应子题目 3）怎么写

论点展开是全文核心，阅卷对这部分最苛刻：出现泛泛而谈的空洞表述就会被判低分。

**两段论**优于三段论：两段各约 500 字，能说透；三段各 300 字往往说不深。两段之间换角度互相印证，例如一段讲角色与工件的运转，另一段讲活动机制与变更响应。

每一段按这条因果链展开，并配上项目里的真实细节：

```
业务场景的特殊性 → 关键在于什么 → 设计之初错把什么当成做法（后果） →
深入分析后改成什么 → 解决了什么问题 / 结果如何
```

细节从四个角度补：业务场景（哪些数据、什么时点）、数据量级（笔数、并发、规模）、技术对比（为什么不用方案 B）、运维视角（资源、窗口、监控）。只写「我们用 X 提升了效率」属于低分写法。

## 七、结尾怎么写

结尾是模板重灾区。不要写「项目顺利上线得到一致好评，仍有一些问题，后续我们会改进」——这套写法曝光度最高。

改成两步：

1. **成效**：给出量化结果（时间、占比、笔数、缺陷密度等）；
2. **理解与边界**：复盘该方法的适用条件，理性指出它在实践中的代价或风险（例如快速响应变更会带来需求边界模糊、过度依赖沟通、短期迭代挤压长期架构积累），并给出自己的判断。

这一段的检查点是：含量化数据，且不出现「不足之处／改进措施／下一步将／后续将／有待改进」。

## 八、句式与「活人感」

用因果链句式让阅卷相信你真的做过，而不是背概念：

- 由于某种业务特殊性，笔者深切感受到某方法／某设计是关键环节；设计之初我们错把另一种做法当成方案，导致了某种后果；深入分析后发现另一种做法更好，它解决了什么问题。
- 以某方法为例，我所在团队采用了某种做法，并且出于某种目的还做了另一件事。
- 在面对某种业务特殊性时，笔者意识到某方法的重要性；初步尝试中选错了策略，效果不理想；反思调整后采用更合理的做法。
- 在实际工作中，笔者逐渐理解到某方法的价值；实施某策略后，团队不仅提升了效率，还解决了某个具体难题。

句式只是引子，硬核内容（场景、数据、取舍）才是过线的基础。AI 生成的内容必须逐句改写：句式雷同、四平八稳的 AI 腔会被识别为模板文。

## 九、项目材料前置：先有 PRD，再写背景

决定论文质量的是产品与业务的系统化理解，而不是技术名词的密度。

- 手头有项目材料最好；没有材料时，先让大模型按「产品概述／目标用户／产品特性／功能需求／非功能需求／验收标准」生成一份 PRD，再据此写项目背景与模块划分；
- PRD 里确定的业务模块就是正文实例的取材范围，能显著降低「内容太假」的风险；
- 同一份 PRD 可跨题型复用（换题不换项目），只调整论述角度。

## 十、素材层：项目素材卡与冲突故事库

论文的上下限由素材决定，动笔前先把素材填成结构化的一页，不要在写作时现编。这一节是流程性要求：**先有卡，再落笔**。

### 10.1 项目素材卡（八项，缺一项就别动笔）

| 字段 | 要填什么 | 判断标准 |
|---|---|---|
| 行业与规模 | 行业、业务量级（用户数／笔数／门店数）、业务特征 | 能说明「这个行业为什么难」 |
| 周期与投入 | 立项到投产的月份、投资额、团队人数与构成 | 摘要与背景都要用，必须能自圆其说 |
| 团队与我的角色 | 我的岗位与**具体负责的工作项** | 不是「负责架构设计」这种泛写，三处（摘要／背景／论点）都要对得上 |
| 独有业务模块 | 5~6 个本项目特有的业务模块 | 出现「用户管理／权限管理」这类通用模块说明站位不够 |
| 量化指标台账 | 每个模块 1~2 个指标：数据量、并发、时延、准确率、人力工时、成本 | 每个指标都要能在正文被引用一次 |
| 冲突故事 | 2~3 条「错误做法→具体冲突→后果→修正→效果」 | 见 10.2 |
| 组织与工具 | 小组名、岗位分工、会议节奏与时长、看板／文档／工具 | 论点段的现场感锚点从这里取 |
| 适用边界 | 这套方法在本项目哪些模块不适用、代价是什么 | 结尾要用 |

已填示例：行业与规模＝省级农信社小微信贷，日均授信申请数千笔、服务网点数百个；周期与投入＝建设期 9 个月、投资 1860 万元、团队 32 人（按业务域分四个小组）；我的角色＝系统分析师，负责需求分析与建模、接口与数据模型设计、跨小组集成协调；独有模块＝授信申请、额度测算（公积金／纳税／流水三种口径）、审批放款、还款结息、贷后预警；量化台账＝单笔办理由 3 个工作日压到当日、额度测算偏差由两成收敛到一成以内、迭代目标达成率由六成升到九成以上；组织与工具＝迭代固定两周、四个业务域小组、需求管理平台与看板；适用边界＝贷款账务与结息这类强一致性模块不适合用模糊的需求边界驱动。

### 10.2 冲突故事库（每条五要素）

```
错误做法：项目初期我们把〈什么〉当成了〈什么〉
具体冲突：〈谁〉按〈口径 A〉做、〈谁〉按〈口径 B〉理解，冲突出现在〈接口／字段／组名／规则口径〉上
后果：〈可量化的返工、延误、投诉、偏差〉
修正做法：〈改成了什么，最好是一条可复述的规则或模板〉
效果：〈量化结果〉
```

要求：**冲突必须具体到接口名、字段名、小组名或规则口径**，不能只写「沟通不畅导致返工」。同一项目的冲突故事可跨题复用（换题不换项目）：Scrum 题讲「待办列表排序权与站会变汇报会」，数据题讲「分块策略与过期规则」，讲的是同一个项目的不同侧面。

示例（承接上表）：错误做法＝把产品待办列表当成一份在线需求文档来管理；具体冲突＝各小组组长按排期协商优先级，额度与风控组的条目长期沉底，客户经理绕开平台走线下审批；后果＝迭代目标达成率只有六成，功能上线后使用率低；修正做法＝由业务部门真正对价值负责的人担任产品负责人，条目按客户价值与合规风险排序，Scrum Master 只保证条目在迭代计划会议前完成细化与估算；效果＝达成率升到九成以上，客户经理开始主动提条目。

### 10.3 术语对齐（与题面同词）

从题面抽取术语清单，作为 `check-essay.ps1 -RequireTerms` 的输入，并遵守**题面用词优先**：题面写「迭代」就不能只写「Sprint」，题面写「产品待办列表」就不能只写「Backlog」。常见同义异文对照：

| 题面可能用词 | 常见异文（答题时须换成题面用词） |
|---|---|
| 迭代 | Sprint、冲刺 |
| 迭代计划会议／迭代评审会议／迭代回顾会议 | Sprint 计划／评审／回顾会议 |
| 产品待办列表／迭代待办列表 | 产品 Backlog／Sprint Backlog |
| 产品增量 | 增量、可交付成果 |
| 数据分片 | 分库分表、Sharding |
| 检索增强生成 | RAG |

## 十一、子题目三问的回应规则

- **子题目 1**（项目与我的工作）：摘要与项目背景两处呼应，摘要给结论，背景给细节。
- **子题目 2**（方法概述）：分类名称全部显性命中，`check-essay.ps1 -RequireTerms` 用来机械核对。
- **子题目 3**（项目如何落地）：问题与措施必须**回挂**到子题目 2 的分类上（是角色的问题、工件的问题还是某个活动的问题），否则会被判成另写了一个项目。

## 十二、结构层：锚点句、机制命名与落点表

判卷人扫读时先看「这一段在回哪个子题目」。结构层要做的就是替他把答案递到眼前。

### 12.1 三问→六段落点表

动笔前先落这张表，一格一格填；填不出来说明素材还不够（回到第十节补卡）。

| 段落 | 回应哪个子题目 | 落点 |
|---|---|---|
| 摘要 | 子题目 1 | 行业痛点＋项目与角色＋技术视角＋成效 |
| 第 2 段（项目背景） | 子题目 1 | 战略依据、投入资源、独有模块、技术栈给理由 |
| 第 3 段（技术方法说明） | 子题目 2 | 题面列出的分类**逐项**写全，用词与题面一致 |
| 第 4 段（论点一） | 子题目 3 | 回挂子题目 2 的**第 1 类**分类（如「角色与工件」） |
| 第 5 段（论点二） | 子题目 3 | 回挂子题目 2 的**第 2 类**分类（如「活动机制」） |
| 第 6 段（结尾） | 子题目 3 | 量化成效＋方法的适用边界 |

### 12.2 段落锚点句

每个论点段的**首句**必须显性回挂子题目，让阅卷一眼看到「这段在回答什么」。自撰句首模板：

1. 〈分类名称〉的落地最先受到考验。
2. 〈分类名称〉的运转是第二个关口。
3. 真正难的不是〈技术〉本身，而是〈分类名称〉怎么在项目里落到人头上。
4. 〈目标〉能否成立，取决于〈分类名称〉是否被设计进去。
5. 项目进行到〈阶段〉时，〈分类名称〉的问题先暴露出来。
6. 〈分类名称〉决定了这套方案能不能在〈约束〉下继续跑。

锚点句之后先给判断、再给故事：先一句「问题出在〈哪儿〉」，再展开「初期我们怎么做错了」。

### 12.3 机制命名与名单预告

- **命名**：论点段以「××机制／××治理／××编排／××策略」命名，把整段的论点立成可复述的名词，例如「以用户故事为核心的需求拆分机制」「每日站会驱动的沟通协作机制」「以权限过滤为核心的检索治理机制」「以幂等与降级为核心的编排策略」。
- **名单预告**：在第一个论点段之前加一句，把两条机制的名字一次列出，例如「要让它真正成立，关键在于两条机制：〈机制一〉与〈机制二〉」。这一句是给「切合题意」打的最便宜的广告。
- **禁忌**：名单预告必须是一句连贯的话，**不得**写成「第一……第二……」或分行列表；机制命名要与子题目 2 的分类对得上，不能只起好听的标题。

## 十三、可信度与深度（数字口径、对比论证、代价句、反套话）

这一层四条规则的力度不同：**代价句是硬项**（不达标即判失败），其余三条是提示（不影响 PASS，但要在交付说明里逐条回应或改掉）。

### 13.1 数字三要素（提示）

关键数字尽量给全「**口径＋时点＋样本**」里的至少一项，例如「按项目组三个同类模块的返工统计」「上线后头三个月的运行数据」「离线评测集一千二百条问句上的命中率」。两类写法要当心：

- **推演式数字**（「假如沿用旧方案，工期可能延长一成半」）：全文最多一处，且必须写明是推演口径（「按类似项目的经验估算」），否则容易被读成编造。门禁把「假如／可能／预计」与数字同段的情况标为 `C1a`。
- **整数百分比堆叠**（20%、30%、15%……）：超过 2 处会被读成拍脑袋。门禁标 `C1b`。
- 论点段里数字 ≥3 处却没有任何口径词（口径／统计／实测／压测／抽样／样本／评测／评估／监测／验收／测算）时，门禁标 `C1c`。

### 13.2 对比论证（提示）

至少写一处「A 方案为什么不行」：评估过什么、为什么放弃、最终选了什么，词面可用「评估过／放弃了／与…相比／最终选择」。整篇找不到对比词时，门禁标 `C2`。

### 13.3 结尾代价句（硬项）

结尾除量化成效外，必须有一句**锚在项目内**的代价或适用边界，例如「〈模块〉这类强一致场景并不适合用模糊的需求边界驱动，我们为此单独保留了详细设计评审」。门禁要求结尾段命中「代价／局限性／适用边界／不适合／不适用／前提条件／权衡」之一，否则判不达标（`C3` 硬项）。

### 13.4 反套话（提示）

「极大地提升／高度重视／得到一致好评／提供了有力支持／打下了坚实基础／显著提升」这类句子把可核查的事实换成了空话。门禁统计到 3 处以上标 `C4`；改法是把空话换成数字与事实——谁、在什么场景、提升了多少。

## 十四、双框分界与交付（硬约束）

论文是摘要框与正文框两个输入框，交付物也必须分框，不能给一段连排文本。

- **源稿约定**：第 1 段＝摘要；紧接一行分界标记 `<!-- BODY -->`（单独占一行）；其余段落＝正文。标记是 HTML 注释，`check-essay.ps1` 与 `make-essay-doc.ps1` 都会整块剥掉，不参与字数统计。
- **门禁强制**：标记缺失、重复、与其它文字同行、或不在第 1 段之后，一律判不达标；门禁会打印 `A 分框:` 一行（摘要框／正文框各多少段多少字、标记是否在位），`SUMMARY` 行给出 `marker=true/false`。
- **生成两种 .doc**：`make-essay-doc.ps1` 不带参数时输出「**批注版**」——正文前插入 `摘要框（N 字／上限 300）` 与 `正文框（N 字／2000~2500，共 M 段）` 两个标题，并在**每一段之前**加一行 `第 k 段｜职能（回应子题目 x）｜M 字`（正文第 1 段＝项目背景、第 2 段＝技术方法说明、末段＝结尾，中间各段＝论点一／二……）；加 `-Plain` 输出「无标注版」，只有摘要段与正文段，供考场直接粘贴。默认文件名分别是 `论xxx.doc` 与 `论xxx-无标注版.doc`。
- **标注行不属于答卷内容**：交付时要说清；正文里仍然不得出现「摘要」「背景」「子题目」这些字眼。
- **交付回复也要分栏**：文件和聊天回复都要把摘要与正文分开呈现，并标出各框字数；只贴一段连排文本属于交付不合格（这正是本约定要根治的问题）。
- **脚本改动后的自检**：`.ps1` 必须始终是带 BOM 的 UTF-8。用编辑器/工具改完脚本后要确认 BOM 还在（`node scripts/verify-manifest.mjs` 与 CI 都会拦），否则 Windows PowerShell 5.1 按 ANSI 误读中文、脚本直接报语法错；本地可跑 `tests/out/ci-sim.ps1` 全量回归。

## 十五、交付与 Word 生成

```powershell
# 分框标注版（默认）：摘要框与正文框分栏，给使用者对照
& "<skill-directory>/scripts/make-essay-doc.ps1" -MdPath "D:\out\论题目.md"
# 形态: 分框标注版（摘要框／正文框已分栏）
# 段数: 7  分界标记: 有
# 摘要框: 291 字（上限 300）
# 正文框: 2339 字（2000~2500），共 5 段  正文纯汉字: 2058

# 无标注版（考场直接粘贴）
& "<skill-directory>/scripts/make-essay-doc.ps1" -MdPath "D:\out\论题目.md" -Plain

# 门禁（分界标记是硬项，未 PASS 不得交付）
& "<skill-directory>/scripts/check-essay.ps1" -MdPath "D:\out\论题目.md" `
  -RequireTerms '角色','工件','活动','产品负责人','Scrum Master','开发团队','产品待办列表','迭代待办列表','产品增量','迭代计划会议','每日站会','迭代评审会议','迭代回顾会议'
```

工程坑（都已踩过）：

- PowerShell 命令行会把中文引号与破折号弄丢，脚本内必须用 `[char]0x201C`／`0x201D`／`0x2014` 构造；
- `.ps1` 必须保存为**带 BOM 的 UTF-8**，否则 Windows PowerShell 5.1 按 ANSI 误读中文；**改完脚本要立刻确认 BOM**（编辑工具常常把它写没）；
- 目标 `.doc` 被 Word 占用时 `WriteAllText` 会抛异常，脚本已做重试与另存 `_v2.doc`；
- 用编辑工具大段替换后要回读文件，检查段落数、重复段与是否吞掉相邻段落；
- **注释要整块剥**：只按「行首是 `<!--`」过滤会把多行注释的中间行当成正文段落（生成脚本已经修掉，改脚本时别退回去）；
- **CRLF 稿子**：分界标记的正则行尾要写 `[ \t]*\r?$`，否则 Windows 下 `Set-Content` 写出的稿子会被误判「缺标记」；
- **`<p>` 计数是 CI 契约**：分栏标题与说明行一律用 `<h3>`／`<div>`，且 HTML 属性用单引号，避免触发「正文无直引号」检查；
- **默认文件名别用 `Path.ChangeExtension(path, $null)`**：Windows PowerShell 5.1（.NET Framework）会保留结尾的点，拼出来是「论xxx..doc」；用 `GetFileNameWithoutExtension` 再拼后缀（CI 与本地镜像都有断言）。
- 被调用的 `.ps1` 里 `exit` 会结束整个 PowerShell 进程：如果一条命令里「先跑门禁、再生成 doc」，要在各自独立的进程/调用里执行。

## 十六、通用默写检查表

- 摘要 ≤300（含标点），独立成部分，且不出现「摘要」二字
- 摘要段之后有**唯一一行** `<!-- BODY -->` 分界标记
- 正文 2000~2500（含标点），合计不超 2800
- 部分齐备且详略合理：背景、技术方法说明、论点两段、结尾
- 无标题、无「背景／子题目」字眼、无「第一／首先／一是」式分点、无 Markdown 粗体
- 子题目 2 列出的分类一个不漏，正文逐项回挂
- 每个论点至少一条项目真实业务实例，正文中至少 3 段带具体数字
- 结尾有量化成效与对方法的理性认识，不出现「不足之处／改进措施／下一步将」
- 建设期只出现在摘要；中文引号已替换，正文无直引号
- 已生成两种 `.doc`：**批注版**（默认，分框＋逐段职能与字数标注）＋无标注版（`-Plain`），交付时摘要与正文分栏呈现
- 结尾除量化成效外，有一句**锚在项目内**的代价／适用边界（C3 硬项）
- 关键数字给过口径／时点／样本；推演式数字 ≤1 处且写明推演口径，整数百分比 ≤2 处
- 至少有一处「评估过 A、为什么放弃、最终选 B」的方案对比
- 没有「极大地提升／高度重视／一致好评／有力支持」这类套话（≤2 处）
- 动笔前已填「项目素材卡」八项，冲突故事库 ≥2 条，且冲突具体到接口／字段／组名／规则口径
- 已落「三问→六段落点表」，每个论点段都标了它回挂的是子题目 2 的哪一类分类
- 两个论点段各有**锚点句**，并以「××机制／××治理／××编排」命名
- 第一个论点段之前有**一句**机制名单预告（不是分点标号），两条机制名与子题目 2 的分类对得上

## 十七、口径变更记录（相对旧版）

- 旧版：严格 10 段、全文含标点 2500~2800、首段兼作摘要、禁写「摘要」字眼、全文禁第一人称、结尾写 2~3 条不足与改进。该口径与机考的摘要／正文双框及 300＋2500 硬限制不符，已废弃。
- 新版：摘要 ≤300 独立成部分、正文 2000~2500、部分配比制、结尾写理解而非问题、第一人称放开为「笔者／我们」。
- 仍保留：不写「背景／子题目」字眼、禁分点标号、禁标题、中文引号码点构造、BOM 要求。
- 本次增补（C 可信度与深度＋D 评分与工具）：新增第十三节「数字三要素（口径／时点／样本、推演式数字、整数百分比）、对比论证、结尾代价句（C3 硬项）、反套话」，门禁按 `C1a／C1b／C1c／C2／C4` 给提示、按 `C3` 判硬项，并在输出里增加**提示分档**一行；`make-essay-doc.ps1` 的批注版改为**逐段标注职能与字数**；自评技能升级为**五维打分**（按官方占比给档位），写作技能新增「自评—重写闭环」步骤；另有一份**仅本地**的「范文结构指纹对比」脚本（不入库）。
