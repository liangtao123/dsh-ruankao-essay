# 软考系分论文写作口径（2026-10 机考）

> 适用：系统分析师／系统架构设计师论文科目。本文件是插件内唯一的字数与结构真相源，`check-essay.ps1`、`make-essay-doc.ps1`、三个技能与 Web 面板都按本文件实现。
> 本文件只写公开的考试事实与自撰的写法说明，不摘录任何第三方付费资料的原文。

---

## 一、交付规格（硬约束）

机考论文分**摘要**与**正文**两个输入框，控件会实时计字符数：摘要框超过 300 字符无法继续输入，正文框超过 2500 字无法提交。因此按下面的双框口径写作与自检。

| 项目 | 要求 |
|---|---|
| 摘要 | **≤300 字（含标点）**，目标 280~300；独立成部分，但正文里不写「摘要」二字 |
| 正文 | **2000~2500 字（含标点）**，目标 2300~2500；2500 是机考硬上限 |
| 段落数 | 不锁死段数，按下面的部分配比自然成段；`check-essay.ps1` 只对摘要与正文总字数判硬项 |
| 标题 | 不写标题，也不写「摘要／背景／子题目」这些字眼 |
| 分点 | 不用「第一／第二」「首先／其次」「一是／二是」式列举，改用因果链叙事 |
| 人称 | 放开：可用「笔者／我们／我所在团队」；摘要里必须有身份交代（「本人」或「笔者」） |
| 引号 | 中文引号「“”」，正文不得出现直引号 |
| 时间 | 建设期（`YYYY年M月`）只写在摘要里，正文不重复 |
| 实例 | 每个论点至少一条项目内真实业务实例（业务场景＋数据量＋结果） |
| 收尾 | 写成效与对方法的理性认识，**不写**「不足之处／改进措施／下一步将」这套模板 |

## 二、部分与字数配比

| 部分 | 字数（含标点） | 内容要点 |
|---|---|---|
| 摘要 | ≤300 | 行业与业务痛点 → 我的角色与主要工作 → 本文的技术视角或创新点 |
| 项目背景 | 400~500 | 战略依据、投入资源、工期、独有业务模块；解释「为什么要做」 |
| 技术方法说明（回应子题目 2） | 400~500 | 题目列出的分类名称逐项写全、显性点题；说明各自在本项目中的落点 |
| 论点一（回应子题目 3） | 约 500 | 业务场景 → 关键决策 → 错误做法与后果 → 修正后的做法 → 结果 |
| 论点二（回应子题目 3） | 约 500 | 同上，换一个角度（另一类角色、另一类工件或另一类活动） |
| 结尾 | 300~450 | 成效（量化）＋对该方法的深入理解与边界认识 |

正文合计约 2000~2400，正好落在机考 2000~2500 区间内。

## 三、摘要怎么写

摘要不写「摘要」二字，直接起笔，三段意思串成一段：

1. **行业与业务背景**：本行业的业务特点与当下痛点，点明项目要解决什么，突出行业特色而不是通用套话。
2. **我的角色与任务**：用「本人」或「笔者」交代在项目中的岗位与具体职责，落到可验证的工作项。
3. **本文视角**：说明本文要论述的技术方法为什么适配这个业务，指出其中的关键判断或创新点。

摘要里必须出现项目名称、建设期与投资额（金额带「万」）、项目角色，这三项同时是门禁的检查项。

## 四、项目背景怎么写

这个部分考察站位，不是考技术清单。常见的低分写法是罗列六七个框架名（SpringBoot、Vue、Redis……）而对建设目的一字不提。

- 写清**战略依据**：业务侧的压力、合规要求、竞争或政策变化；
- 写清**投入资源**：投资规模、团队规模与构成、建设期；
- 写清**独有业务模块**：用本项目特有的业务场景（如信贷的「额度测算」「贷后预警」），避免「用户管理」「权限管理」这类通用模块；
- 用「概括＋理由」介绍技术栈：选它是因为什么业务特性，而不是把技术名堆成一句。

## 五、技术方法说明（回应子题目 2）怎么写

题目第 2 问通常是理论性的、概念性的：要你概述某个方法、模型或流程的分类。这部分是显性点题的得分区。

- 题目列出的分类名称**逐项写全**，用词与题目一致，一个不漏；
- 每个分类用一两句说清「是什么」，再补一句「在本项目中落点在哪」；
- 字数写到 400~500：漏写常见，但字数太少会让阅卷认定作答态度不足；
- 漏写不等于乱写：如果连题目在问什么都没把握，换题。

敏捷题（2023/05 系分试题三）需要写全的是：角色（产品负责人、Scrum Master、开发团队）、工件（产品待办列表、迭代待办列表、产品增量）、活动（迭代、迭代计划会议、每日站会、迭代评审会议、迭代回顾会议）。

## 六、论点展开（回应子题目 3）怎么写

论点展开是全文核心，阅卷对这部分最苛刻：出现泛泛而谈的空洞表述就会被判低分。

**两段论**优于三段论：两段各约 500 字，能说透；三段各 300 字往往说不深。两段之间换角度互相印证，例如一段讲角色与工件的运转，另一段讲活动机制与变更响应。

每一段按这条因果链展开，并配上项目里的真实细节：

```
业务场景的特殊性 → 关键在于什么 → 设计之初错把什么当成做法（后果） →
深入分析后改成什么 → 解决了什么问题 / 结果如何
```

细节从四个角度补：业务场景（哪些数据、什么时点）、数据量级（笔数、并发、规模）、技术对比（为什么不用方案 B）、运维视角（资源、窗口、监控）。只写「我们用 X 提升了效率」属于低分写法。

## 七、结尾怎么写

结尾是模板重灾区。不要写「项目顺利上线得到一致好评，仍有一些问题，后续我们会改进」——这套写法曝光度最高。

改成两步：

1. **成效**：给出量化结果（时间、占比、笔数、缺陷密度等）；
2. **理解与边界**：复盘该方法的适用条件，理性指出它在实践中的代价或风险（例如快速响应变更会带来需求边界模糊、过度依赖沟通、短期迭代挤压长期架构积累），并给出自己的判断。

这一段的检查点是：含量化数据，且不出现「不足之处／改进措施／下一步将／后续将／有待改进」。

## 八、句式与「活人感」

用因果链句式让阅卷相信你真的做过，而不是背概念：

- 由于某种业务特殊性，笔者深切感受到某方法／某设计是关键环节；设计之初我们错把另一种做法当成方案，导致了某种后果；深入分析后发现另一种做法更好，它解决了什么问题。
- 以某方法为例，我所在团队采用了某种做法，并且出于某种目的还做了另一件事。
- 在面对某种业务特殊性时，笔者意识到某方法的重要性；初步尝试中选错了策略，效果不理想；反思调整后采用更合理的做法。
- 在实际工作中，笔者逐渐理解到某方法的价值；实施某策略后，团队不仅提升了效率，还解决了某个具体难题。

句式只是引子，硬核内容（场景、数据、取舍）才是过线的基础。AI 生成的内容必须逐句改写：句式雷同、四平八稳的 AI 腔会被识别为模板文。

## 九、项目材料前置：先有 PRD，再写背景

决定论文质量的是产品与业务的系统化理解，而不是技术名词的密度。

- 手头有项目材料最好；没有材料时，先让大模型按「产品概述／目标用户／产品特性／功能需求／非功能需求／验收标准」生成一份 PRD，再据此写项目背景与模块划分；
- PRD 里确定的业务模块就是正文实例的取材范围，能显著降低「内容太假」的风险；
- 同一份 PRD 可跨题型复用（换题不换项目），只调整论述角度。

## 十、子题目三问的回应规则

- **子题目 1**（项目与我的工作）：摘要与项目背景两处呼应，摘要给结论，背景给细节。
- **子题目 2**（方法概述）：分类名称全部显性命中，`check-essay.ps1 -RequireTerms` 用来机械核对。
- **子题目 3**（项目如何落地）：问题与措施必须**回挂**到子题目 2 的分类上（是角色的问题、工件的问题还是某个活动的问题），否则会被判成另写了一个项目。

## 十一、交付与 Word 生成

```powershell
# 生成 Word 可打开的 .doc（首段＝摘要）
& "<skill-directory>/scripts/make-essay-doc.ps1" -MdPath "D:\out\论敏捷开发方法（Scrum）.md"
# 摘要字数: 296  正文字数: 2384  正文纯汉字: 2120  段数: 6

# 门禁：未输出 PASS 不得交付
& "<skill-directory>/scripts/check-essay.ps1" -MdPath "D:\out\论敏捷开发方法（Scrum）.md" `
  -RequireTerms '角色','工件','活动','产品负责人','Scrum Master','开发团队','产品待办列表','迭代待办列表','产品增量','迭代计划会议','每日站会','迭代评审会议','迭代回顾会议'
```

工程坑（都已踩过）：

- PowerShell 命令行会把中文引号与破折号弄丢，脚本内必须用 `[char]0x201C`／`0x201D`／`0x2014` 构造；
- `.ps1` 必须保存为**带 BOM 的 UTF-8**，否则 Windows PowerShell 5.1 按 ANSI 误读中文；
- 目标 `.doc` 被 Word 占用时 `WriteAllText` 会抛异常，脚本已做重试与另存 `_v2.doc`；
- 用编辑工具大段替换后要回读文件，检查段落数、重复段与是否吞掉相邻段落。

## 十二、通用默写检查表

- 摘要 ≤300（含标点），独立成部分，且不出现「摘要」二字
- 正文 2000~2500（含标点），合计不超 2800
- 部分齐备且详略合理：背景、技术方法说明、论点两段、结尾
- 无标题、无「背景／子题目」字眼、无「第一／首先／一是」式分点、无 Markdown 粗体
- 子题目 2 列出的分类一个不漏，正文逐项回挂
- 每个论点至少一条项目真实业务实例，正文中至少 3 段带具体数字
- 结尾有量化成效与对方法的理性认识，不出现「不足之处／改进措施／下一步将」
- 建设期只出现在摘要；中文引号已替换，正文无直引号

## 十三、口径变更记录（相对旧版）

- 旧版：严格 10 段、全文含标点 2500~2800、首段兼作摘要、禁写「摘要」字眼、全文禁第一人称、结尾写 2~3 条不足与改进。该口径与机考的摘要／正文双框及 300＋2500 硬限制不符，已废弃。
- 新版：摘要 ≤300 独立成部分、正文 2000~2500、部分配比制、结尾写理解而非问题、第一人称放开为「笔者／我们」。
- 仍保留：不写「背景／子题目」字眼、禁分点标号、禁标题、中文引号码点构造、BOM 要求。
