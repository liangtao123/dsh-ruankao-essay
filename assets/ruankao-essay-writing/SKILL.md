# 软考系统分析师论文写作总纲

用本技能代替即兴发挥：先查题库（`ruankao-essay-bank` 技能），再按下面的口径成稿，最后跑门禁。

## 触发场景

- 用户给出「论×××」题目＋三个子题目，要求写一篇论文（押题、模拟、考场备用）。
- 用户上传自己的论文 docx，要求改写／润色／提分。
- 用户给出新题目，要求「按软考论文格式」产出成稿。

## 交付规格（硬约束，逐条自检）

机考论文分**摘要框**与**正文框**，控件按字符数硬限制：摘要超 300 输不进去，正文超 2500 提交不了。

| 项目 | 要求 |
|---|---|
| 摘要 | **≤300 字（含标点）**，目标 280~300；独立成部分；段内**不写「摘要」二字** |
| 正文 | **2000~2500 字（含标点）**，目标 2300~2500 |
| 结构 | 部分配比制：项目背景 400~500 → 技术方法说明（回应子题目 2）400~500 → 论点两段各约 500（回应子题目 3）→ 结尾 300~450 |
| 标题 | **不写标题**，也不写「背景」「子题目」这些字眼（模板化会扣分） |
| 分点 | 不用「第一／第二」「首先／其次」「一是／二是」式列举，改用因果链叙事 |
| 人称 | 放开：「笔者／我们／我所在团队」均可；摘要里必须有身份交代（「本人」或「笔者」） |
| 时间 | 建设期（`YYYY年M月`）**只写在摘要**，正文不再重复 |
| 引号 | 中文引号「“”」，不要直引号 |
| 实例 | 每个论点至少配一条**项目内真实业务实例**（业务场景＋数据量＋结果） |
| 收尾 | 量化成效＋对该方法的理性认识与边界；**不写**「不足之处／改进措施／下一步将」 |
| 交付 | `.doc`（Word 可直接打开）＋ `.md`（源稿），文件名与题目一致 |

详细的写法说明与句式参考见 `references/writing-rules.md`。

## 流程

1. **查题**：用 `ruankao-essay-bank` 技能列目录，确认题目出处（年份/试题号）、该题型的理论骨架、写作规格与官方评分口径。
2. **备材料**：项目材料优先用用户提供的真实项目；用户没有材料时，先按 `references/writing-rules.md` 第九节生成一份 PRD（产品概述／目标用户／产品特性／功能需求／非功能需求／验收标准），再据此写背景与实例，并把数据标注为示例。
3. **建骨架**：把子题目 2 要求的分类**逐项列出**（名称必须与题目用词一致，一个不漏），作为回应段的论点，并规划两部分字数。
4. **配实例**：每个分类各写一条项目做法，落到具体业务（如「日终批量与月度结息」「放款金额取额度上下限」「额度测算三种口径的迭代取舍」），不要只谈技术名词。
5. **写成稿**：按部分配比写作；摘要先写，控制在 300 以内；论点用两段论；结尾写成效与理解。
6. **对子题目 3**：问题与解决办法要**回挂**到子题目 2 的分类（是角色的问题、工件的问题，还是某个活动的问题）。
7. **自检**：运行 `scripts/check-essay.ps1`——脚本检查四类内容：A 双框字数与格式（摘要 ≤300、正文 2000~2500、无标题/粗体/直引号/禁写字眼/分点标号）；B 部分职能（摘要含身份与金额周期、建设期只在摘要、结尾含量化且无模板化改进表述）；C 实例密度（正文中至少 3 段含具体数字）；D 术语覆盖（`-RequireTerms` 给出的分类名称必须全部命中，对应子题目 2 的显性点题）。**未输出 PASS 不得交付**。

```powershell
& "<skill-directory>/scripts/check-essay.ps1" -MdPath "D:\out\论题目.md" `
  -RequireTerms '分类名称1','分类名称2'
```

常用参数：`-AbstractMax 300`、`-BodyMin 2000`、`-BodyMax 2500`（字数口径变化时改这里，不改脚本逻辑）、`-StripAbstractLabel`（贴进来的稿子带「摘要：」前缀时自动剥离）。

8. **生成交付物**：调用 `scripts/make-essay-doc.ps1` 把 `.md` 转成 Word 可打开的 `.doc`（脚本已处理中文标点与编码的坑，并分别打印摘要与正文字数）。

## 子题目回应规则（决定成败）

- **子题目 1**：摘要含项目、行业、时间、金额、角色与职责；项目背景补细节（战略依据、投入资源、工期、独有业务模块）。
- **子题目 2**：**必须显性点题**——题目列出的分类名称要在正文出现，并说明各自在本项目中的落点；这是最容易丢分的地方。理论名称宁多勿漏，回应段写到 400~500 字。
- **子题目 3**：问题→措施→效果，且与子题目 2 的分类一一对应；效果给量化数据；两段论各约 500 字。

## 通用默写检查表（每篇写完自检）

- 摘要 ≤300（含标点）、独立成部分、段内无「摘要」二字，且含身份、金额、周期
- 正文 2000~2500（含标点）；部分齐备且详略合理（背景／技术方法说明／论点两段／结尾）
- 无标题、无「背景／子题目」字眼；无「第一／首先／一是」式分点；无 Markdown 粗体 `**`
- 建设期只出现在摘要；中文引号已替换、正文无直引号
- 子题目 2 列出的分类一个不漏，正文逐项回挂
- 每个论点至少一条项目真实业务实例；正文中至少 3 段带具体数字
- 结尾有量化成效与对方法的理性认识，不出现「不足之处／改进措施／下一步将」

## 生成 Word 文档

用调用运算符直接执行脚本（**不要**套一层 `pwsh -File`，本机 shell 内没有 `pwsh` 可执行文件）：

```powershell
& "<skill-directory>/scripts/make-essay-doc.ps1" -MdPath "D:\path\essay.md" -OutPath "D:\path\论题目.doc"
```

脚本要点（若需手写，务必照做）：

- 版式：A4、页边距 2.54/3.17cm、宋体小四（12pt）、首行缩进 2 字符、行距 1.5、两端对齐；
- **PowerShell 命令行会把中文引号「“”」和破折号「——」弄丢，必须用 `[char]0x201C`、`[char]0x201D`、`[char]0x2014` 构造**；
- 脚本本身必须以**带 BOM 的 UTF-8** 保存：本机是 Windows PowerShell 5.1，无 BOM 的 .ps1 会按 ANSI 误读，中文字符串被破坏后脚本直接报错；
- 输出用带 BOM 的 UTF-8；文件被 Word 占用时脚本会重试，仍失败则另存 `*_v2.doc`；
- 脚本按「第一段＝摘要」分别打印**摘要字数 / 正文字数 / 正文纯汉字 / 段数**；摘要须 ≤300、正文 2000~2500。

字数口径提醒：脚本统计时**会剥掉 Markdown 的 `**` 粗体标记**，所以 md 里不要用 `**`（既影响计数又属于考场不认的格式），写完先自查 `**`、`一是/首先` 这类分点残留。

## 边界

- 只做「软考系分论文」这一件事；不做范本抄袭——项目背景与数据由用户确认，未提供时用用户自己的项目或明确标注为示例数据的自拟背景。
- 用户给了自己的原文时，**保留其项目事实与数据**，只改结构、语气、字数与错别字取向（按用户要求决定是否保留原文用字）。
- 不复制任何第三方课程的范文、句式原文或统计数据；句式一律用自撰表述承载因果链。
