# 软考系统分析师论文自评与批改

对成稿做**逐部分体检**，输出可直接照改的问题清单；只依据公开的考试规范与阅卷口径，不引用任何课程资料或他人作品。

## 输入

- 一份论文成稿（`.md` / `.doc` 正文）＋对应题目与三个子题目；
- 若用户只给了正文没给题目，先要求补充题目，否则无法判断切题。

## 一、先用脚本做机械检查

机械项不靠肉眼，直接量。契约：源稿**第一段＝摘要**，摘要段之后有一行分界标记 `<!-- BODY -->`，其余段落＝正文。**先确认稿子分了框**：缺标记、或拿到的是「摘要与正文混成一段连排文本」，直接判交付不合格、先让其补标记再往下评。

```powershell
# 分框标注版（默认，看摘要框／正文框各多少字与段数）
& "<skill-directory>/../ruankao-essay-writing/scripts/make-essay-doc.ps1" -MdPath "<成稿>.md" -OutPath "<临时>.doc"
# 无标注版（考场粘贴用）
& "<skill-directory>/../ruankao-essay-writing/scripts/make-essay-doc.ps1" -MdPath "<成稿>.md" -Plain

# 门禁（含分框分界、格式、部分职能、实例密度、术语覆盖；SUMMARY 需 marker=true 且 pass=true）
& "<skill-directory>/../ruankao-essay-writing/scripts/check-essay.ps1" -MdPath "<成稿>.md" -RequireTerms <子题目2的分类名称…>
```

| 机械项 | 合格标准 | 不合格怎么报 |
|---|---|---|
| 分框分界 | 摘要段之后有唯一一行 `<!-- BODY -->`，`SUMMARY` 为 `marker=true` | 缺标记／标记重复／位置错：报「分框未成立」，先修再评其余项 |
| 摘要字数 | ≤300（含标点） | 给差额与需删的字；摘要过简（<200）也报，官方口径视为扣分项 |
| 正文字数 | 2000~2500（含标点） | 超 2500 是机考硬限，必须压；低于 2000 报缺口 |
| 部分配比 | 背景 400~500／技术方法说明 400~500／论点各约 500／结尾 300~450 | 指出哪个部分过胖或过瘦，给建议增删字数 |
| 论点段数 | 2 段为佳（各约 500） | 3 段以上提示「说不透」，1 段提示「单薄」 |
| 标题 | 无 | 指出具体行 |
| 「背景／子题目」字眼 | 无（摘要二字也不写入正文） | 指出具体句 |
| 「第一／首先／一是」式分点 | 无 | 逐处列出并给改写句 |
| Markdown 残留 | 无 `**`、无列表符号 | 逐处列出 |
| 建设期出现位置 | 只在摘要 | 指出重复出现的段落 |
| 结尾模板化 | 不出现「不足之处／改进措施／下一步将／后续将／有待改进」 | 逐处列出并给改写句 |
| 结尾量化 | 含时间／占比／笔数／密度类数据 | 提醒补指标 |

## 二、再按部分逐个体检

| 部分 | 检查什么 |
|---|---|
| 摘要 | 是否含行业与业务痛点、项目名称、建设期与金额、本人角色与主要工作、本文的技术视角；是否**点题**（出现题目关键词）；是否控制在 300 以内 |
| 项目背景 | 是否说明「为什么做」与战略依据、投入资源、工期；技术栈是否**给理由**而非罗列；模块是否是本行业独有（出现「用户管理／权限管理」这类通用模块要扣） |
| 技术方法说明（子题目 2） | 题目列出的分类**名称是否齐全**、是否显性点题、是否解释「是什么／在本项目怎么落地」；字数是否到 400~500 |
| 论点一／论点二（子题目 3） | 是否按「业务特殊性→关键决策→错误做法与后果→修正→结果」展开；是否有场景、数据量级、技术对比或运维视角；是否只谈技术不谈业务 |
| 结尾 | 是否有量化成效；是否写出了对该方法的理解与边界（可提局限），而不是项目缺点＋改进计划 |

## 三、五类高频扣分（按严重度排序）

1. **偏题**：子题目 2 的分类缺项、或用词与题目不一致——必须改，属硬扣分（官方口径里「切合题意」占约 30%）。
2. **字数越界**：摘要超 300 或正文超 2500 在机考里根本输不进去／提交不了——必须改。
3. **内容空洞或不真实**：只有概念与书本话、没有项目细节，或数据明显编造——必须改（官方口径里「实践性」占约 20%，且虚构属不及格情形）。
4. **模板化**：标题、「背景／子题目」字眼、分点标号、套路化结尾（问题＋改进）——必须改。
5. **表达与逻辑**：段落之间没有因果链、论点两段各说各话——建议改（「表达能力」占约 15%）。

按下面结构输出，不要泛泛而谈：

```

   分框 摘要段后 <!-- BODY --> ✓ / SUMMARY marker=true ✓ / 交付两版 doc ✓
   摘要 296 ✓ / 正文 2384 ✓ / 部分配比：背景 470 ✓ 技术方法 430 ✓ 论点 520+505 ✓ 结尾 380 ✓
   无标题 ✓ / 分点 2 处 ✗ / 正文直引号 0 ✓ / 结尾模板化 0 ✓

二、逐部分结论
   摘要：已含行业痛点与角色，但技术视角一句话带过 —— 建议改

   论点二：只有技术描述、缺业务数据量级 —— 必须改
   结尾：量化只有「明显提升」，无指标 —— 建议改

三、改写建议（逐条给出原句 → 修改句）
   原句：……
   改为：……

   是否可提交：否；优先修掉 2 处「必须改」。
```

## 五、边界

- **不编造项目数据**：用户没给指标时，建议补指标并把数值标注为「示例，请替换为真实数据」。
- **不照抄他人作品**：只按规范给结构与写法建议，不提供他人成稿的段落，也不引用第三方课程资料。
- 机械项与子题目覆盖是硬项，先报；文采类建议放最后，不要淹没硬伤。

## 与其他技能的分工

- `ruankao-essay-bank`：查题目、理论骨架、评分口径 → 动笔前用。
- `ruankao-essay-writing`：双框口径成稿与 Word 交付 → 动笔时用。
- 本技能：对已成稿做体检与改写建议 → 交稿前用。
